# .githooks/ — механический контроль правил git

Эти хуки — не замена промпт-инструкциям агентов, а вторая, механическая
линия защиты для тех же правил: git не различает, какой агент (или человек)
делает коммит — все они работают от одного пользователя и одной git-личности
в одной рабочей копии. Поэтому хуки проверяют СОДЕРЖИМОЕ и СОСТОЯНИЕ, а не
"кто" совершает действие. Почему роль-специфичная защита требует уже
CI/отдельного сервисного аккаунта, а не локального git-хука, и как пришли к
текущей схеме — см. `docs/HISTORY.md`.

## Установка (один раз на репозиторий)

```
git config core.hooksPath .githooks
```

Обычные хуки в `.git/hooks/` не версионируются вместе с репозиторием — если
не сделать `core.hooksPath`, эти файлы просто не будут вызываться. Настройка
входит в Вызов 0 `devops-engineer` (подготовка репозитория, см.
`.claude/agents/devops-engineer.md`); её можно сделать и вручную.

## pre-commit

1. **Защита веток** — блокирует прямой коммит в `develop`,
   `release-candidate`, `master`/`main`: всё, что коммитится, коммитится на
   `cycle/<NNN>-<slug>`, а в защищённые ветки попадает только `--ff-only`
   мерджем от `devops-engineer` (см. основной README, "Ветки и релизы").
   Коммит во время `git merge` (существует `MERGE_HEAD`) пропускается — это
   нужно для разрешения конфликтов при sync `develop` → cycle. Не-ff мердж
   прямо в защищённую ветку этим исключением не легализуется: его ловят
   правило `--ff-only` у `devops-engineer` и `pre-push` (у нового
   merge-коммита нет прогона CI).
2. **Сканирование секретов** — гоняет [gitleaks](https://github.com/gitleaks/gitleaks)
   по застейдженным изменениям, если он установлен:
   `gitleaks git --staged --redact --no-banner` (gitleaks 8.19+), а для
   старых версий без подкоманды `git` — `gitleaks protect --staged ...`.
   Если gitleaks нет — используется заметно более слабая встроенная проверка
   на несколько распространённых паттернов (AWS-ключи, приватные ключи,
   `api_key = "..."` и т.п.). Рекомендуется установить gitleaks:
   - macOS: `brew install gitleaks`
   - остальное: см. инструкции в репозитории gitleaks

## pre-push

Внешнее подтверждение через CI перед тем, как что-либо попадает в
защищённую ветку, без модели pull request:

1. Хук сначала читает все пушимые ref. Если ни один не указывает на
   `develop`/`release-candidate`/`master`/`main` (например, пуш
   `cycle/<NNN>-<slug>`), он сразу завершается успешно — без `gh` и без
   обращения к сети.
2. Для пуша в защищённую ветку хук (один раз определив репозиторий через
   `gh repo view`) проверяет у пушимого коммита:
   - check-runs (`gh api repos/<repo>/commits/<sha>/check-runs`) — все
     завершены (`status == completed`) с исходом `success`, `skipped` или
     `neutral`;
   - legacy commit statuses (`.../commits/<sha>/status`) — все в состоянии
     `success` (для внешних CI, отчитывающихся через Statuses API).
   Должна быть хотя бы одна проверка того или другого типа.
3. Если проверок нет вообще, или хотя бы одна не прошла/не закончилась — пуш
   блокируется с пояснением (запушить исходную ветку, дождаться зелёного
   прогона, только потом мерджить сюда `--ff-only`).
4. Работает вместе с правилом из `.claude/agents/devops-engineer.md`: любой
   мердж в `develop`/`release-candidate`/`master` — всегда
   `git merge --ff-only`. Тогда SHA, который пушится в защищённую ветку, —
   ровно тот же коммит, что уже был отдельно запушен (как cycle-ветка,
   `develop` или `release-candidate` на предыдущем шаге) и прогнан через CI,
   поэтому хук проходит сразу. У merge-коммита или чего-то, чего не было на
   исходной ветке, прогонов не будет — пуш заблокируется.
5. Для пуша в защищённую ветку требуются установленный и авторизованный `gh`
   (`gh auth login`), `python3` и репозиторий на GitHub. Если чего-то нет,
   хук БЛОКИРУЕТ пуш в защищённую ветку, а не пропускает его молча.

### Первый пуш свежего репозитория

Единственный легитимный случай обхода — Вызов 0 `devops-engineer`
(подготовка репозитория): защищённые ветки пушатся впервые, CI ещё ни разу
не запускался, и проверять нечего:

```
ALLOW_NO_CI_CHECK=1 git push -u origin master develop
```

Во всех остальных случаях нужно дождаться зелёного CI на исходной ветке.

## Что это НЕ защищает

- Обходится флагом `--no-verify` — хук не защита от того, кто явно решил его
  обойти, а страховка от случайной ошибки (в том числе агента).
- Не работает, если `core.hooksPath` не настроен в конкретной рабочей копии —
  клон репозитория на другой машине эти хуки сам по себе не подхватит.
- `pre-push` не даёт разграничения прав по ролям (кто именно может пушить в
  `master`) — он проверяет "прогнан ли коммит через CI", а не "кто его
  пушит" (это один и тот же локальный git-пользователь для всех агентов).
  Для настоящего разграничения по ролям нужен отдельный сервисный
  аккаунт/токен с разными правами на разные ветки и branch protection на
  стороне GitHub.
- `pre-push` зависит от `gh` и от того, что CI вообще запускается на пуш
  исходной ветки — если в проекте CI настроен иначе (например, только на
  pull request), проверку нужно адаптировать под реальный триггер.
