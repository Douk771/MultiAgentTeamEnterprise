# Как работать с командой агентов в Claude Code

Пошаговая шпаргалка для ручного режима: что писать агентам в чате, по шагам,
для нового проекта и для существующего. Модель процесса и автоматический
режим (Workflow) описаны в [README.md](README.md).

## Шаг 0 — открыть проект и проверить, что агенты подхватились

1. Установите команду в проект по разделу «Установка» в
   [README.md](README.md) (вся папка `.claude/` + `.githooks/`) и откройте
   Claude Code в корне проекта.
2. Сделайте sanity-check перед реальной работой — спросите в чате:
   «Какие саб-агенты доступны в этом проекте?» (или выполните `/agents`).
   Должны быть все 10: codebase-analyst, product-analyst, architect,
   backend-developer, frontend-developer, code-reviewer, qa-engineer,
   devops-engineer, technical-writer, legal-counsel. Если списка нет —
   `.claude/agents/` лежит не в корне проекта. Папки, начинающиеся с точки,
   файловые менеджеры по умолчанию скрывают — проверьте через терминал
   (`ls -a`).

## Как обращаться к конкретному агенту

Достаточно назвать агента по имени и описать задачу обычным текстом — Claude
Code способен сам понять, кого делегировать, по полю `description` в файле
агента. Но для конвейера, где порядок критичен (архитектор должен отработать
раньше разработчиков, а не наоборот), надёжнее вызывать агента явно:

> Используй агента product-analyst: вот идея — [описание].

Работает и с `@`-упоминанием:

> @product-analyst вот идея — [описание]

Дальше в этом файле — конкретные фразы для каждого шага, которые можно
копировать как есть, подставляя свою задачу.

## Ветки: коротко перед тем, как начать

Вся работа над одной задачей идёт в отдельной ветке цикла
`cycle/<NNN>-<slug>`, ответвлённой от `develop`. `master`,
`release-candidate` и `develop` — защищённые ветки: в них попадают только
`--ff-only`-мерджи, и делает их только `devops-engineer`. Прямых коммитов в
защищённые ветки нет ни у кого. Подробная модель — в README, раздел «Ветки и
релизы». Для сценариев ниже важно:

- ветки создаёт, подтягивает `develop` и мерджит **только**
  `devops-engineer`;
- backend-developer, frontend-developer, qa-engineer, codebase-analyst и
  code-reviewer (если правит код) сами коммитят свои изменения на текущей
  cycle-ветке;
- у product-analyst, architect, technical-writer и legal-counsel нет Bash —
  их документы коммитит devops-engineer отдельным коротким вызовом
  «Фиксация документов»:
  > Используй агента devops-engineer: зафиксируй документы агентов на
  > текущей cycle-ветке («Фиксация документов»).

## Сценарий А — новый проект с нуля

Отправляйте сообщения по одному, дожидаясь ответа агента перед следующим шагом:

0. **Подготовить репозиторий и завести ветку цикла.**
   > Используй агента devops-engineer: подготовь cycle-ветку от develop для
   > новой задачи — [коротко название задачи].

   Если репозитория или ветки `develop` ещё нет (совсем чистый старт),
   devops-engineer сначала выполнит **Вызов 0 — подготовку репозитория**:
   `git init` при необходимости, начальный коммит (если коммитов ещё нет),
   `master` и `develop`, `core.hooksPath` и первый пуш. Это делается один
   раз на проект. Минимальный CI в GitHub Actions devops-engineer добавит
   первым коммитом этой первой cycle-ветки — в `develop` он попадёт при
   интеграции цикла. Первый пуш защищённых веток, пока CI ещё ни разу не запускался, —
   единственный легитимный случай `ALLOW_NO_CI_CHECK=1 git push ...`; во всех
   остальных случаях обходить проверку CI нельзя.

1. **Идея → ТЗ.**
   > Используй агента product-analyst: вот идея продукта — [описание].
   > Составь SPEC.md.

   Затем «Фиксация документов» у devops-engineer (фраза выше). Прочитайте
   SPEC.md — особенно блок «Что стоит проверить с заказчиком до начала
   кодирования». Если предположения не устраивают — поправьте файл руками
   или попросите product-analyst переделать конкретный пункт.

2. **ТЗ → архитектура.**
   > Используй агента architect: прочитай SPEC.md и подготовь ARCHITECTURE.md
   > и API_CONTRACT.md.

   Затем снова «Фиксация документов». Это вторая и последняя точка, где
   стоит остановиться и посмотреть глазами перед тем, как пойдёт код —
   дальше исправления обходятся дороже. architect заодно кладёт рядом с
   API_CONTRACT.md машиночитаемую схему контракта (OpenAPI и т.п.) — она
   нужна для контрактной проверки.

3. **Реализация.** Можно в одном сообщении попросить сразу обоих — Claude Code
   сам разберётся с параллельным выполнением:
   > Используй агентов backend-developer и frontend-developer: пусть каждый
   > реализует свою часть по ARCHITECTURE.md и API_CONTRACT.md.

   Чтобы видеть прогресс по отдельности — зовите их двумя разными
   сообщениями.

3а. **Контрактная проверка — быстро и дёшево, до ревью кода.**
   > Используй агента qa-engineer: прогони контрактную проверку (раздел
   > "Контрактная проверка" в твоей роли) по машиночитаемой схеме из
   > ARCHITECTURE.md/API_CONTRACT.md.

   Это не написание тестов, а прогон готового инструмента: если backend и
   frontend разошлись по форме интерфейса (поле называется иначе, другой
   формат даты и т.п.), дешевле поймать это здесь, чем после полного ревью.
   Если расхождение есть — отправьте нужному разработчику на исправление и
   повторите этот шаг, прежде чем переходить к шагу 4.

4. **Ревью.**
   > Используй агента code-reviewer: проверь diff текущей задачи.

   При ручном вызове code-reviewer не будет молча чинить находки сам и не
   будет молча передавать их разработчикам — он закончит отчёт вопросом
   вроде «Исправить эти находки самому сейчас, или передать
   backend-developer/frontend-developer как обычно?» и остановится.

   Обычный путь — отдать разработчикам:
   > Передай разработчикам как обычно.

   > Используй backend-developer/frontend-developer (смотря к чьей части
   > относится находка): исправь блокирующие находки ревью [список или
   > ссылка на предыдущий ответ].

   Если находок немного и удобнее, чтобы ревьюер поправил их сам:
   > Исправь сам.

   Тогда code-reviewer использует Edit, коммитит правку на cycle-ветке и
   явно перечислит, что изменил (файл, строка, было → стало) — кроме тестов:
   их он не пишет и не правит никогда, а сообщает, какому агенту передать
   написание теста.

   Повторяйте шаг 4, пока блокеров не останется. В автоматическом режиме
   (`build-app-implement.js`) вопроса не будет: скрипт сообщает
   code-reviewer, что вызов автоматический, и находки всегда уходят
   разработчикам.

5. **Тесты.**
   > Используй агента qa-engineer: напиши функциональные тесты по критериям
   > приёмки из SPEC.md и прогони их.

   Если найдены баги — так же, как в п. 4, отправляйте их нужному
   разработчику и просите qa-engineer перепроверить.

6. **Подтянуть develop в cycle-ветку.**
   > Используй агента devops-engineer: смёржи develop в текущую cycle-ветку
   > (первая часть "Вызова 2").

   Если `develop` с момента ответвления не менялся — мерджить нечего,
   devops-engineer так и сообщит, и проверки ниже не нужны. Если `develop`
   ушёл вперёд — **с конфликтом или без** — проверки после мерджа
   обязательны: само по себе чистое слияние не гарантирует, что код из двух
   веток вместе работает так же, как по отдельности. Если возник конфликт в
   коде — сначала попросите нужного разработчика его разрешить. Затем:
   > Используй агента code-reviewer: проверь diff мерджа develop в
   > cycle-ветку (режим "ревью после мерджа").

   > Используй агента qa-engineer: повтори контрактную проверку после
   > интеграции develop в cycle-ветку (второй вызов раздела "Контрактная
   > проверка").

   > Используй агента qa-engineer: перепрогони полную регрессию после
   > интеграции develop в cycle-ветку ("Вызов 3").

   Дальше — только если все три чистые.

7. **Закрыть цикл — на cycle-ветке, до мерджа в develop.** Это первый цикл
   на проекте, поэтому CURRENT_STATE.md ещё нет — самое время его завести,
   пока SPEC.md и ARCHITECTURE.md цикла под рукой. Сообщения независимы:
   > Используй агента codebase-analyst: составь CURRENT_STATE.md (файла ещё
   > нет — режим "Полное сканирование") и закоммить его на текущей
   > cycle-ветке.

   > Используй агента product-analyst: обнови раздел "О проекте" в README и
   > добавь запись в раздел "Unreleased" CHANGELOG по своей роли
   > ("Вызов 2") — по итогам этого цикла.

   Пользовательские гайды (`technical-writer`) здесь НЕ вызываются — это
   момент релиза, см. «Релиз» ниже.

8. **Интеграция в develop.** Это не деплой в прод — цикл попадает в общий
   ствол `develop` и деплоится в dev/staging; прод-релиз — отдельный шаг:
   > Используй агента devops-engineer: зафиксируй документы, запушь
   > cycle-ветку, дождись зелёного CI, смёржи её в develop (--ff-only) и
   > задеплой в dev/staging (вторая часть "Вызова 2").

   Если devops-engineer сообщает, что мердж не состоялся (`merged: false`),
   — цикл не завершён: разберитесь с указанной причиной, прежде чем идти
   дальше. При continuous delivery (каждый цикл — сам себе релиз)
   переходите к разделу «Релиз» сразу после этого шага.

## Релиз — отдельное событие, не на каждый цикл

Момент, когда `develop` фактически идёт в прод, — после одного цикла или
после нескольких, решает человек. Всё движется линейно `cycle → develop →
release-candidate → master`, только `--ff-only`; в `release-candidate`
никто не коммитит.

**Проверка релиза:**
> Используй агента devops-engineer: перенеси develop в release-candidate
> (--ff-only, "Вызов 3").

> Используй агента qa-engineer: прогони полную регрессию на release-candidate
> ("Вызов 4" — релизная регрессия).

Если что-то упало — исправления делаются **не** на `release-candidate`, а
в отдельном fix-цикле от `develop`:
> Используй агента devops-engineer: создай fix-цикл `cycle/<NNN>-rc-fix-<версия>`
> от develop для исправления багов релизной регрессии.

Дальше — исправление у нужного разработчика, ревью и проверка QA по
найденным багам, интеграция в `develop` (шаг 8 сценария А), снова перенос
`develop → release-candidate` и повтор релизной регрессии.

**Публикация** — только когда регрессия чистая и `develop` совпадает с
`release-candidate` (если с момента проверки в `develop` попали новые
циклы — повторите проверку):
> Используй агента devops-engineer: создай релизную ветку
> `cycle/<NNN>-release-<версия>` от develop.

> Используй агента product-analyst: перенеси накопившиеся записи из раздела
> "Unreleased" CHANGELOG под новую датированную версию ("Вызов 3").

Только после этого (не параллельно):
> Используй агента technical-writer: обнови/опубликуй пользовательские гайды
> по свежей записи CHANGELOG этого релиза.

Шаг с technical-writer нужен, только если продукту нужна такая
документация; для внутреннего инструмента его можно пропустить. Наконец:
> Используй агента devops-engineer: зафиксируй документы, дождись зелёного
> CI, проведи релизную ветку по цепочке develop → release-candidate → master
> (--ff-only), поставь тег версии и задеплой в прод.

## Дальше — вторая и последующие задачи на этом же проекте

Полное сканирование заново не нужно — CURRENT_STATE.md уже есть и
поддерживается в каждом цикле:

0. **Завести новую cycle-ветку** от `develop` (той же фразой, что в шаге 0
   сценария А).

1. **Быстрая проверка на дрейф окружения.**
   > Используй агента qa-engineer: прогони существующий набор функциональных
   > тестов и зафиксируй базовый результат.

   После зелёного предыдущего цикла это проходит быстро. Если что-то
   красное — что-то изменилось независимо от команды (зависимости,
   окружение, ручные правки), и стоит разобраться, прежде чем продолжать.

2. **Новая задача.**
   > Используй агента product-analyst: прочитай CURRENT_STATE.md. Нужно
   > сделать следующее — [описание новой задачи]. Составь SPEC.md.

   Дальше — шаги 2–8 сценария А. В close-out (шаг 7) codebase-analyst
   увидит, что CURRENT_STATE.md уже есть, и выберет режим «Обновление»:
   > Используй агента codebase-analyst: обнови CURRENT_STATE.md по итогам
   > этого цикла и закоммить на текущей cycle-ветке.

   Режим агент сообщает первой строкой отчёта («Режим: обновление» или
   «Режим: полное сканирование»).

   Полное сканирование стоит повторять изредка (раз в несколько циклов) или
   если есть подозрение, что код меняли в обход команды агентов.

## Сценарий Б — существующий (наполовину готовый) сервис

Отличие только в первых шагах — дальше сценарий тот же, что в А:

1. **Завести cycle-ветку.**
   > Используй агента devops-engineer: подготовь cycle-ветку для новой
   > задачи — [коротко название задачи].

   Если `develop` в репозитории ещё нет, devops-engineer сначала выполнит
   Вызов 0 — сверившись с уже принятой в проекте схемой веток и CI-конфигом
   и предложив, как встроить модель поверх неё.

2. **Карта текущего состояния.**
   > Используй агента codebase-analyst: разбери текущий проект и составь
   > CURRENT_STATE.md. Обязательно укажи, где в проекте уже есть документация
   > и описания тест-кейсов, если они есть.

3. **Базовый прогон тестов — до каких-либо изменений.**
   > Используй агента qa-engineer: найди в CURRENT_STATE.md, как запускается
   > существующий набор тестов, прогони его и зафиксируй базовый результат.

4. **Задача → ТЗ**, теперь с контекстом:
   > Используй агента product-analyst: прочитай CURRENT_STATE.md. Нужно
   > сделать следующее — [описание задачи]. Составь SPEC.md.

   Дальше — шаги 2–8 сценария А (architect сам прочитает CURRENT_STATE.md
   и SPEC.md — пересказывать ничего не нужно) и раздел «Релиз», когда
   решите выпускать.

## Если в проекте уже есть своя документация и тест-кейсы

Специально просить ничего не нужно: `codebase-analyst` на онбординге
перечисляет в CURRENT_STATE.md, что и где уже существует (формат changelog,
README, каталог тест-кейсов), а `product-analyst`, `backend-developer` (для
API-документации), `qa-engineer` (для тест-кейсов) и `technical-writer`
(для гайдов) дополняют именно найденное, в его формате, а не заводят
параллельные версии. Явная просьба в шаге 2 сценария Б — просто
дополнительная страховка.

## Параллельная работа над несколькими циклами

Если есть несколько независимых задач — необязательно ждать, пока
предыдущий цикл дойдёт до `develop`. Параллелизм получается через несколько
независимых сессий Claude Code, у каждой своя рабочая копия репозитория: в
одной директории нельзя держать выписанными две ветки, поэтому для второй
задачи нужен `git worktree add` (общий `.git`, легче по диску) или
отдельный `git clone`.

**Уже автоматически:**
- Номер и имя следующей cycle-ветки devops-engineer вычисляет по
  существующим веткам, поэтому две сессии не выберут одинаковое имя. Перед
  стартом он показывает список ещё не интегрированных cycle-веток — если
  новая задача пересекается с активной по смыслу, дешевле развести их
  заранее.
- Сборка и тестовый стенд настраиваются с учётом параллельного цикла на той
  же машине (имя compose-проекта и порты — по номеру цикла), а qa-engineer
  перед прогоном проверяет, что стенд его собственный.
- CURRENT_STATE.md обновляется в close-out на cycle-ветке **после**
  подтягивания `develop`, поэтому codebase-analyst видит изменения цикла,
  интегрированного раньше, и дописывает свои поверх, а не перезаписывает
  файл вслепую.
- Конфликт в коде при подтягивании `develop` — штатная ситуация (шаг 6
  сценария А): разработчик разрешает конфликт, затем обязательные ревью
  после мерджа, контрактная проверка и регрессия. Это цена цикла, который
  пришёл вторым.

**Нужно сделать руками при подготовке второй рабочей копии:**
- Скопировать реальные значения `.env` — в git их нет (только
  `.env.example`).
- Если в проекте есть общий сервис, установленный прямо на машину (например,
  локальный Postgres/Redis вне docker-compose), — это блокер для
  параллельной работы: агенты предупредят, но развести такой сервис по
  копиям (или контейнеризовать) можно только руками.
- Дать сессиям понятные названия и решать, какая задача интегрируется
  первой, — агенты это не координируют.

Если задачи независимы по коду (разные модули/страницы) — цена параллелизма
минимальна. Если пересекаются — результат всё равно будет корректным за счёт
проверок после мерджа у второго цикла, но выигрыш по времени меньше.

## Юридические вопросы (по требованию, не в общем конвейере)

`legal-counsel` не встроен в обычную цепочку шагов и ни один
workflow-скрипт его не вызывает автоматически — зовите вручную, когда есть
конкретный юридический вопрос по праву РФ:

> Используй агента legal-counsel: продукт собирает [какие данные]. Проверь,
> что нужно с точки зрения 152-ФЗ, и подготовь/обнови политику
> конфиденциальности.

Затем «Фиксация документов» у devops-engineer. Если необходимость видна уже
на этапе ТЗ (сбор персональных данных, платная подписка по оферте),
`product-analyst` сам предложит позвать `legal-counsel`.

Это не замена практикующему юристу: агент обязан предупреждать, когда
документ или оценка требуют проверки юристом, но для значимых решений
(регистрация оператора ПДн, трансграничная передача данных и т.п.)
полагаться только на это не стоит.

## Общее правило: не пересказывайте файлы руками

Агенты сами читают SPEC.md, ARCHITECTURE.md, CURRENT_STATE.md и т.д. из
проекта. Реплика агенту обычно сводится к «прочитай файл X и сделай свою
часть работы». Исключение — когда вы поправили файл руками между шагами и
хотите явно на это указать («я изменил критерии приёмки во втором пункте
SPEC.md, учти это»).

## Когда переходить на автоматизацию (Workflow)

С ручного режима стоит начинать: виден каждый промежуточный результат и
можно поправить курс. Когда цепочка отработала предсказуемо, те же шаги
прогоняются сценариями `.claude/workflows/`:

- цикл — тремя отдельными запусками с остановкой для проверки человеком
  между ними: `build-app-plan.js` (ветка, онбординг, SPEC.md) →
  `build-app-architecture.js` (ARCHITECTURE.md/API_CONTRACT.md) →
  `build-app-implement.js` (реализация, проверки, close-out, интеграция в
  `develop`);
- релиз — двумя: `build-app-release-validate.js` (`develop →
  release-candidate` + релизная регрессия, fix-циклы при необходимости) и,
  отдельным осознанным действием после чтения её результата,
  `build-app-release-publish.js` (CHANGELOG, гайды, `master`, тег,
  прод-деплой).

Каждый следующий скрипт запускается отдельным вызовом Workflow с
результатом предыдущего в `args`. Разделение релиза сохраняется и при
полной автоматизации: прод-деплой с реальными секретами не идёт
автоматическим продолжением зелёной регрессии (обоснование — в
[docs/HISTORY.md](docs/HISTORY.md)). Аргументы и порядок запуска — в
README, раздел «Быстрый старт».

### Остановка по бюджету или сбою — не перезапускайте с нуля

Актуально только для автоматического режима.

Если скрипт остановился сам (`blocked: 'budget'` — не хватило бюджета до
дорогого шага) или упал на середине из-за разового сбоя (сеть, ошибка
инструмента) — не запускайте его заново с нуля: это повторно оплатит уже
пройденные дорогие шаги. Резюмируйте тот же прогон через `resumeFromRunId`
инструмента Workflow (ID прогона возвращается при первом запуске) — уже
завершённые вызовы `agent()` с теми же аргументами вернутся из кэша, а
выполнится только то, что не успело. Если остановка была по бюджету —
увеличьте лимит перед резюмированием.

Оговорки: это работает только в той же сессии, где был первый запуск; и это
не способ «переиграть с другими вводными» — если поменять промпт или
аргументы раннего вызова, его кэш не совпадёт, и он вместе со всем зависимым
пересчитается заново.
